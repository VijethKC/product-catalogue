# How AI was used

This repository was built with an AI coding agent under continuous human review. This
document records the working method, the guardrails, and — importantly — the places where
the AI was wrong and how that was caught.

The short version: AI wrote most of the keystrokes; a human owned the architecture, the
scope, every commit, and every claim of "done".

---

## 1. Tools

| Role | Tool |
|---|---|
| Agent | OpenCode — an agent harness that reads files, runs commands, edits the repo, and runs the test suite |
| Model | A frontier chat model driving the agent (no inline autocomplete, no IDE ghost text) |
| Verification | The repository's own tooling: `tsc`, Vitest, Supertest, nock, Vite build, Docker Compose |
| Data | Fake Store API (live), plus committed fixtures for offline tests |

No code was generated by a separate "generate the whole app" pass. Every change arrived as
a reviewable diff in a session that could read the existing code first.

---

## 2. Workflow

```
spec (human)  →  plan doc  →  one step per session  →  tests  →  live check  →  review  →  commit
```

1. **Spec before code.** `docs/PLAN.md` fixed the scope, the API contract, the error table
   and the build order before a line of application code existed. Decisions that would
   otherwise be made implicitly by the model were made explicitly in writing.
2. **One step per session.** `docs/IMPLEMENTATION_STEPS.md` breaks the work into seven
   steps with their own work items and acceptance criteria. Each step is a separate commit.
   Small increments kept the diffs reviewable and the context stable.
3. **Tests alongside, not after.** Every step added tests in the same change. If a test
   could not be written, the design was usually wrong.
4. **Live verification.** Passing tests were never treated as proof. Each step ended with
   real HTTP calls, and later a real browser and a real SMTP server.
5. **Human review before commit.** Nothing was committed or pushed without explicit
   approval. The reviewer read the diff, not just the summary.

---

## 3. Prompt strategy

What worked, in order of impact:

- **Point at the spec, not at the goal.** "Implement Step 3 as written in
  `docs/IMPLEMENTATION_STEPS.md`" produced a scoped change. "Add email" would have produced
  a guess about transport, validation, and error handling.
- **State the constraints that are easy to violate.** "No new dependencies without
  justification", "do not modify unrelated files", "mirror the conventions in
  `routes/products.ts`". These are cheap to say and expensive to fix later.
- **Ask for the failure path explicitly.** Every prompt about an endpoint named its error
  cases (unknown product, invalid payload, delivery failure). The 502 branch and its test
  exist because the failure was part of the request, not because the model volunteered it.
- **Require a verification command.** "Run typecheck, tests and build, and show the output"
  turned "should work" into evidence.
- **Ask for assumptions.** Where the brief was ambiguous — how many products are "top
  rated" per category — the instruction was to state an assumption and proceed, which is
  how `FEATURED_PER_CATEGORY` came to exist as configuration instead of a magic number.

What did not work: long prose descriptions of intent. Concrete file paths, existing
patterns, and explicit error cases did the work.

---

## 4. Guardrails in the repository

`AGENTS.md` is read by the agent on every session and encodes the non-negotiables:

- read the specs before changing code;
- follow the approved architecture and existing conventions;
- no unnecessary dependencies;
- no unrelated file edits;
- tests alongside implementation;
- never trust generated code — review it critically;
- no secrets, `.env.example` only;
- run the relevant tests before declaring a task complete;
- **do not commit or push until the user approves.**

The last rule matters most. An agent that can commit can quietly rewrite history; an agent
that must stop and show its work keeps the human in the loop at the only moment that
matters.

---

## 5. What the human reviewed on every change

Not a vibe check — a fixed list:

1. **The diff**, line by line. Especially: did it touch a file it had no business touching?
2. **The tests.** Do they assert behaviour, or do they assert that the code was written?
   A test that mirrors the implementation proves nothing.
3. **The error paths.** What happens on a 500 from upstream, an empty list, a malformed
   body, an SMTP outage?
4. **The contract.** Did the response shape change without the shared schema changing?
5. **The claims.** Every number in a summary was re-derived from a command's output.

## 6. Where the AI was wrong

These are real, not hypothetical. Each one was caught before it shipped, and the fix is in
the code.

### 6.1 Malformed JSON returned `500`

`POST /api/enquiries` was the first endpoint to accept a body. `express.json()` rejects
invalid JSON by throwing a `SyntaxError` with `type: "entity.parse.failed"`. The generated
`errorHandler` only understood `HttpError`, so a client sending a broken body received
`500 INTERNAL_ERROR` — a server error for a client mistake, and a misleading one.

**Caught by:** writing the test `rejects a malformed JSON body as a validation error`
before declaring the step done. It failed: a malformed body produced `500`, not `400`.

**Fixed by:** an explicit `isBodyParseError` branch in `middleware/errorHandler.ts` that
returns `400 VALIDATION_ERROR`. The test now covers it.

**Lesson:** the happy path and the validation path were both written and tested; the
*parser* path was nobody's job until a test asked for it.

### 6.2 The verification harness lied (IPv4 vs IPv6)

Docker was unavailable during the enquiry step, so a ~60-line SMTP sink was written to
capture mail locally. It bound to `127.0.0.1`. The API connected to `localhost`, which
resolved to `::1` on this machine, and the send failed.

The failure looked like an application bug: `502 EMAIL_UNAVAILABLE` from a code path that
had already passed its unit tests.

**Caught by:** checking `lsof -nP -iTCP:1025 -sTCP:LISTEN` and seeing the listener on the
IPv4 address only, rather than trusting the error message.

**Fixed by:** binding the sink to all interfaces. The application code was correct.

**Lesson:** when a test harness fails, suspect the harness. An AI-written tool is still
code, and a false negative here could have hidden a real bug — or sent someone chasing one
that did not exist.

### 6.3 The Node version contradicted itself

`package.json` declared `engines.node >= 22.12` and the Docker images used
`node:22-alpine`, but the README said "Node.js 20+". A contributor on Node 20.5 would have
followed the README and hit a Vite failure.

**Caught by:** a consistency pass during Step 6, comparing the documented requirement
against `engines` and the Dockerfile.

**Fixed by:** the README now states 22.12+, matching what is actually tested. Recorded as
decision 14 in `docs/DECISIONS.md`.

**Lesson:** documentation drift is invisible to tests. It needs its own review pass.

### 6.4 Plan drift: MSW was planned, `vi.mock` was used

`docs/PLAN.md` named MSW for web tests. The implementation used `vi.mock` on the typed API
client instead — a reasonable call, but it was made silently at the time and only noticed
when writing the testing section of this document.

**Fixed by:** recording the deviation and its reasoning in `docs/DECISIONS.md` (decision
13) rather than rewriting the plan to match the outcome. A plan that is quietly edited to
agree with the code teaches a reviewer nothing.

**Lesson:** deviations are fine; undocumented deviations are not. If the plan and the code
disagree, one of them needs to say so out loud.

### 6.5 Polish the agent did not think of

The first frontend pass left the footer floating mid-page on short routes, and submitting
an empty search navigated to `/search?q=` with an empty state instead of returning home.

**Caught by:** the human using the app.

**Fixed by:** `flex min-h-screen flex-col` with a `flex-1` main, and a redirect when the
trimmed query is empty.

**Lesson:** tests assert what you thought to assert. Someone has to actually look at the
screen.

## 7. Verification beyond tests

Each step ended with evidence, not a summary:

| Step | Beyond the test suite |
|---|---|
| 1–2 | `curl` against the live API: featured ids, category split, `404` for an unknown id, `400` for a non-numeric id |
| 3 | A local SMTP sink captured the multipart message; the HTML part was inspected to confirm `&lt;script&gt;` escaping |
| 4 | The app was driven in a real browser: search, category navigation, detail, form states |
| 5 | `docker compose up --build` on a real Docker daemon: all services healthy, SPA fallback, proxied API, enquiry visible in Mailpit, API running as `uid=1000(node)` |
| 6 | This document and `docs/PULL_REQUEST.md` checked against the code, command by command |

Step 5 is the clearest example of why this matters. The step was written with a caveat that
Docker was unavailable, so the images had never been built. When Docker was installed, the
stack came up and passed every check — but that was a fact established by running it, not
by reasoning about it.

---

## 8. What was not delegated

- **Scope.** Which features exist, and which are explicitly out of scope.
- **Architecture.** The two seams, the layer rules, and the decision to keep the contract
  shared.
- **Ambiguity calls.** How many products are "top rated" per category; whether a missing
  product is a `404` or a `400`.
- **Commit messages and timing.** Every commit was reviewed and approved by a human.
- **Any claim of "done".** Done means the command was run and the output was read.

---

## 9. Honest limits

- **The AI cannot see the product.** Layout and polish problems were found by a person
  looking at the app, not by any test.
- **The AI cannot validate its own environment.** The Step 5 caveat and the IPv6 harness
  bug are the same failure mode: reasoning about a system it could not fully observe.
- **Tests written by the same model that wrote the code share its blind spots.** The
  malformed-JSON gap is exactly that: the model tested what it had implemented. Human
  review of *what was not tested* is the control.
- **Volume is not quality.** The value here is the small diff, the documented assumption,
  and the failing test that was fixed — not the number of lines produced.
